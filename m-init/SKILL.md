# Init — Project Bootstrap

> **TL;DR** — Detect repo mode + host tool (0) → scaffold code if greenfield (1) → ground yourself in the real repo (2) → one confirm gate (3) → write the artifacts, delegating what siblings own (4) → verify & route (5).

The output is the **agent-facing** layer of a project: a **project brief**, **rules files**, **`.sdd/`**, and a **permissions allowlist**. Everything in it must trace to something that actually exists in the repo — an invented command or convention is worse than an absent one, because every later skill trusts these files (`m-ask` Phase 1, `m-implement` Phase 0, `m-sdd-knowledge`, `m-sdd-constitution` all read the brief).

---

## Phase 0 — Detect mode & host tool

**Repo mode:**

| Signal | Mode | Go to |
|---|---|---|
| No source files (empty repo, or only `README`/`LICENSE`/`.git`) | **Greenfield** | Phase 1 |
| Source files present, no project brief | **Onboard** | Phase 2 |
| A project brief already present | **Refresh** | Phase 2 — diff against reality, propose edits; never silently rewrite |

**Host tool** — which agent actually reads this repo. First hit wins:

1. **An agent file already in the repo** — `CLAUDE.md`/`.claude/`, `AGENTS.md`, `.cursorrules`/`.cursor/`, `.windsurfrules`, `.devin/`. That tool is already in use: extend its file, never add a rival one.
2. **The skills root** — the folder this `SKILL.md` was loaded from: `…/.config/devin/skills` or `<project>/.devin/skills` → Devin CLI; `…/.claude/skills` → Claude Code; `<project>/.cursor/skills` → Cursor.
3. **Ask once** — greenfield, or no signal. Offer the targets this toolkit installs for (`install.sh --tool claude|cursor|windsurf|agents`, or the Devin default). *More than one is a valid answer* — then write the brief once and have each other tool's file link to it rather than duplicating.

**Artifact paths per tool** — defaults only; a path that already exists in the repo always wins over this table, and Phase 3 is where the user corrects it:

| Host tool | Project brief | Rules | Permissions |
|---|---|---|---|
| Claude Code | `CLAUDE.md` (root) | `.claude/rules/*.md` | `.claude/settings.json` |
| Devin CLI | `AGENTS.md` (root) | `.devin/rules/*.md` | — |
| Cursor | `AGENTS.md` + `.cursorrules` pointing at it | `.cursor/rules/*.mdc` | — |
| Windsurf | `AGENTS.md` + `.windsurfrules` pointing at it | — | — |
| Any other / unknown | `AGENTS.md` (root) | `docs/rules/*.md` | — |

**Collision guard:** `install.sh --tool <name> --project …` writes the *generated SDD adapter* to `.claude/CLAUDE.md`, `.cursorrules`, `.windsurfrules`, or `AGENTS.md` — which can be the same path as the brief. If the target file opens with `# SDD Pipeline —`, it is that generated adapter: keep it, put the brief above it under an `<!-- SDD adapter (generated by install.sh) -->` marker, and never regenerate or reflow the adapter body.

Also record: is this a git repo (`git rev-parse --git-dir`), the remote (`git remote -v`), the branches (`git branch -a`), and whether `.sdd/` exists. State the detected mode **and host tool** in one line before doing anything.

## Phase 1 — Greenfield only: create the codebase

Never hand-write a project skeleton you can generate. Ask the user for stack + package manager if not stated (one question, offer the two or three plausible options), then use the ecosystem's own official scaffolder (`npm create …`, `cargo new`, `uv init`, `go mod init`, `dotnet new`, …). Add a test runner and a typecheck/lint script in the same pass — Phase 4's brief needs real commands to cite, and `m-test-driven-development` needs a runner that exists.

`git init` + first commit if there's no repo yet. Then continue into Phase 2 and treat the fresh tree as the evidence.

---

## Phase 2 — Ground

Read before writing. Stop when you have enough for each artifact:

1. **Manifest** — `package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml`: real scripts, real deps, package manager (from the lockfile, not a guess).
2. **Layout** — top two levels of the source tree; what each top-level folder owns.
3. **Entry points** — the boot module, the app/router factory, the config loader.
4. **Existing rules** — every agent file found in Phase 0, plus `CONVENTIONS.md`, `CONTRIBUTING.md`, `.editorconfig`, CI config. These outrank your inference.
5. **Git reality** — branch names on the remote, recent commit-message style (Conventional or not), tags.

If the tree is large, delegate the sweep to a subagent and keep the conclusion. Verify each command you intend to document actually exists in the manifest — do not run installs or builds to find out.

---

## Phase 3 — Confirm gate

Show the exact file list you will create or change, one line each, plus the mode and host tool from Phase 0 and anything you could not determine. Wait for a yes. Files that already exist are shown as *edit*, never as *create*.

---

## Phase 4 — Write the artifacts

| Artifact | Owner | How |
|---|---|---|
| Project brief | this skill | If the host tool has a built-in init/onboarding command (e.g. Claude Code's `/init`), use it for the first draft, then **trim** to the shape below. No such command, or Refresh mode: draft/edit from Phase 2 evidence. |
| Rules files | this skill | Only rules the repo actually has evidence for (below) |
| `.sdd/` | **`m-sdd`** | Offer it; on yes, hand off — it scaffolds `.sdd/` and routes to `m-sdd-constitution` / `m-sdd-knowledge`. Never hand-roll `.sdd/` files here. |
| Permissions allowlist | the host tool's own config skill | Only where the tool has one. Claude Code: `fewer-permission-prompts`, then `update-config`, to allowlist the repo's real test/typecheck/git commands. Other tools: skip it and say so — don't invent a config format. |

**Brief shape** — a reference card the next session reads in full, not documentation:

```md
# <project>
<2–3 lines: what this service/app is, and its one hard boundary>

## Commands        # only scripts that exist in the manifest, one line of intent each
## Architecture    # per top-level module: what it owns, in one line; point at deeper docs
## Binding rules   # the non-obvious invariants: what must never change, what fails closed
## Docs            # pointers to the real design/ops docs and rules files, with paths
```

Keep it under ~100 lines. Anything longer belongs in a doc the brief links to. Every path, command, and rule in it must be one you verified in Phase 2.

**Rules files** — one file per durable, checkable convention; `gitflow.md` is the usual first one (trunk, branch naming, promotion path, remote, commit style). Nothing auto-loads a rules folder — only the brief is loaded for you — so the brief must link each rules file by path. That link is what turns a question the git skills otherwise re-ask into a recorded answer: `m-finishing-a-development-branch` resolves the trunk from `origin/HEAD` and falls back to asking the user (`m-finishing-a-development-branch/SKILL.md:61-68`), and branch naming follows `m-git-commit` conventions (`m-worktree/SKILL.md:88`). Derive the content from the observed branches and commit history, then have the user confirm the promotion path — branch *intent* is not inferable from names alone.

---

## Phase 5 — Verify & route

- Re-read each file you wrote as a whole; fix anything that drifted from the evidence.
- Run the documented typecheck/test commands **as documented** — a command in the brief that doesn't run is the defect this phase exists to catch.
- Commit via `m-git-commit` (`chore: bootstrap agent scaffolding`) if the user wants it committed.
- Route on: greenfield with a feature to build → `m-ask` (it triages to `m-implement` / `m-brainstorming` / `m-sdd`); SDD chosen in Phase 4 → `m-sdd`; otherwise "Done."

---

## Never

- Document a command, path, or convention you did not verify in Phase 2 — no aspirational brief.
- Assume the host tool is Claude Code, or write `.claude/` paths into a Devin/Cursor/Windsurf project — run the Phase 0 detection first.
- Treat a host built-in (`/init`, `fewer-permission-prompts`, `update-config`) as a hard dependency — they exist only in Claude Code; elsewhere, do that step inline.
- Overwrite an existing brief, rules file, settings file, or a generated SDD adapter without showing the diff and getting a yes (Phase 3).
- Hand-roll `.sdd/` state, or hand-edit permissions — those belong to `m-sdd` and the host's config skill.
- Infer the branching model from branch names alone; confirm the promotion path with the user.
- Hand-write a project skeleton an official scaffolder generates (Phase 1).
- Ship a brief that restates what the repo already makes obvious — it earns its place by holding the non-obvious.
